# TravelEase

A working fleet coordination MVP with a FastAPI backend, a React
administrator dashboard, and a React PWA for drivers, passengers, and guardians.

## What's actually implemented (not just scaffolding)

- **Auth and users**: password hashing, JWT sessions, role-based access
  control (`admin` / `driver` / `passenger` / `guardian`), first-admin
  bootstrap, user management, and account deactivation.
- **Organizations**: manage schools, universities, companies, and fleet
  owners; assign organizations to users, vehicles, and routes.
- **Admin dashboard**: manage and edit vehicles, driver profiles, routes,
  schedules, trips, and users; link guardians to passengers; filter by
  organization; review trip history, GPS paths, and stop dwell events;
  view and resolve SOS alerts.
- **Analytics and reports**: filter trip summaries by date, route, vehicle,
  and driver; review daily trips, trip outcomes, duration and delay,
  bookings by route, SOS counts, charts, and downloadable CSV history.
- **Driver dashboard**: see today's assigned routes, vehicle and booked
  passenger count; start/end trips; stream GPS locations with an in-memory
  offline queue and optional screen wake lock; track and manually mark stops;
  edit phone and license details; and raise an SOS alert with current location
  and personal alert status.
- **Passenger dashboard**: browse published routes, book/cancel a seat
  (capacity-enforced against the vehicle), choose a boarding stop, and
  track booked active trips on a live stop map with approximate boarding
  ETA and stale-location warnings; raise an SOS alert.
- **Guardian dashboard**: view passengers linked by an administrator and
  monitor their active booked routes with the same live location details.
- **Notifications and SOS**: poll a role-scoped inbox every 15 seconds with
  unread counts; notify passengers and linked guardians about trip starts,
  approaching boarding stops, delays, trip endings, and SOS alerts.
- **Trip tracking**: record GPS paths and stop arrival/departure events;
  admin history includes route maps and dwell/long-stop details.
- **Automated tests**: backend tests cover authentication, role enforcement,
  organizations, guardian links, analytics, trip/booking flows, notifications,
  and passenger/guardian trip-data isolation.
- **CI pipeline**: GitHub Actions runs backend tests and lint/build checks
  for both `admin-web/` and `govan-app/` on every push and PR (see
  `.github/workflows/ci.yml`).

## Architecture

Modular monolith backend -- one deployable FastAPI app, internally split
into domain modules (`auth`, `users`, `organizations`, `vehicles`,
`drivers`, `routes`, `trips`, `bookings`, `alerts`, `notifications`, and
`reports`).

```
backend/
  app/              # FastAPI application, ORM models, schemas, and routers
  tests/            # pytest suite, isolated test DB per test
admin-web/
  src/              # administrator dashboard
govan-app/
  src/              # driver, passenger, and guardian PWA
  public/            # install icons and static assets
```

## Running it locally

### Backend

```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
```

API docs (auto-generated by FastAPI): http://localhost:8000/docs

**Want demo data instead of starting from zero?** Run this once, from the
`backend/` folder, after installing dependencies:

```bash
python seed.py
```

This creates 5 ready-to-use accounts (all with password `Passw0rd!`), two
vehicles, two routes, and two bookings -- so you can log in and see a
populated dashboard immediately instead of manually registering accounts
every time:

| Role | Email | Notes |
|---|---|---|
| Admin | admin@govan.dev | |
| Driver | dave@govan.dev | assigned to LEB-101, route "Campus Loop" |
| Driver | sana@govan.dev | assigned to LEB-202, route "City Express" |
| Passenger | pat@govan.dev | booked on "Campus Loop" |
| Passenger | ali@govan.dev | booked on "City Express" |

Safe to re-run any time -- it skips anything that already exists instead
of creating duplicates.

**A note on where your data lives:** the database file (`govan.db`) is
always created inside the `backend/` folder itself, regardless of which
directory you happen to run `uvicorn` or `python seed.py` from. Earlier
versions of this project used a path relative to the current working
directory, which could silently create a *new, empty* database if you
launched the server from a different folder (e.g. via an IDE's "Run"
button with a different working directory configured) -- which looks
exactly like your data vanishing. That's fixed now: the path is anchored
to the file's own location, so it's the same database every time no
matter how you start the server. Delete `govan.db` any time you actually
want a clean slate.

### Administrator dashboard

```bash
cd admin-web
npm install
npm run dev
```

Open http://localhost:5173. The first administrator can be registered
through the login page; subsequent admin accounts must be created from
the Users tab or by running the seed script.

If your backend isn't on `localhost:8000`, set `VITE_API_URL` in a
`.env` file inside `admin-web/`.

### Driver and passenger app

```bash
cd govan-app
npm install
npm run dev
```

The Vite development server prints its local URL when it starts. Set
`VITE_API_URL` in `govan-app/.env` if the backend is not at
`http://localhost:8000`.

The app is installable as a PWA (TravelEase name, standalone display, a
`manifest.json`, and 192px/512px icons). Build it with `npm run build`, then
use `npm run preview` to test the production bundle and service worker. The service worker caches
the app shell and serves it for navigation while offline; a visible
"You are offline" banner explains that live API data will resume when
connectivity returns. For production Add to Home Screen and geolocation, serve
the app over HTTPS (localhost is permitted for development).

### Backend tests

```bash
cd backend
python -m pytest tests -v
```

## What's intentionally out of scope for this MVP

Matches the SRS's own MVP/future split -- not omitted by accident:

- Billing/payments, fleet contracts (internal vs external), CCTV,
  RFID attendance, AI-assisted scheduling/route optimization, ride
  sharing, and vehicle rental are all documented in the SRS as
  later-phase modules, not MVP.
- Live location updates here are plain REST calls for simplicity; a
  production build would upgrade the tracking path to WebSocket/MQTT
  as shown in the architecture diagram.
- Auth is deliberately basic (no refresh tokens, no MFA, no password
  reset flow) -- sufficient to demonstrate role separation, not
  production-hardened.

## CI principles applied

- **Fail fast, fail independently**: backend and frontend run as
  separate parallel jobs, so a broken frontend build doesn't mask a
  backend test failure.
- **Reproducible builds**: dependencies install strictly from
  `requirements.txt` / `package-lock.json`, never "whatever's on the
  runner."
- **Nothing merges unverified**: the workflow triggers on every push
  and pull request against `main`/`develop`.
- **Cheap checks before expensive ones**: lint runs before build on
  the frontend job, so obvious mistakes surface in seconds.
